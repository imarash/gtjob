## Deviations and interpretations (no contract changed)
1. **Rule 10 before approval.** `check_tailored(draft=False)` reports `attestation_not_active` exactly as section 8 says.
   Section 7 says a run's `proposed` attestations stay usable until `cvt approve` activates them, so the `check-tailored` command sets
   `attestation_status` to **warn** while the stage is below `approved`, and to **fail** from `approved` on. `--draft` always warns.
   `validate` (WP-14) should call `check_tailored(draft=False)`, or `check_attestation_status`, after approval.
2. Proposed corrections from the current run are applied when checking facts (rule 6). Active ones always are; section 8 says "active", but
   cp1 corrections would otherwise block `assemble` until approval.
3. Mutated fixtures are patch specs (`mutations.json`) applied to the golden in tests, not 26 copied JSON files.
4. **Skills text.** My `item_text` for a skills group is `"Name: kw1, kw2"`. The golden `match.json` quotes (`"AWS, ECS, S3, IAM"`) only pass that way.
   WP-10's `profile.item_text` joins with spaces, so I-2 must align it before swapping the helpers, or `match-check` will reject the golden quotes.
5. Extra checks beyond the brief, all truthfulness-motivated:
   - Skill group labels are checked like terms (`skill_unsupported`).
   - Talking points are checked like bullets (`item_id` is `talking_points[N]`).
   - A placement check applies to non-bullet prose, with `correction` attestations exempt.
   - `match-check` rejects strong/partial requirements with no evidence.
6. `check-tailored` does not compare `profile_sha256` / `jd_sha256` inside `tailored.json` with the run (not specified).
   It does not record `validation.json` as a state artifact (its stage is `validated`; `validate` owns that).
