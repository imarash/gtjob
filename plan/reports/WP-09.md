# WP-09 report: Ingest

## Summary
- `cvtlib/ingest.py`: `Extraction`, `extract_cv` (pdftotext -layout, else pypdf layout + NFKC; `.txt`/`.md` with latin-1
  fallback; `.docx` and OCR via the optional `cvtlib.extras` hook), `clean_cv_text`, `load_jd` (file/text/url), `clean_jd_text`.
- `cvtlib/commands/ingest.py`: `cvt ingest RUN` writes `cv.txt` and `jd.txt`, records `cv_txt`/`jd_txt`, fills `state.ingest`,
  sets stage `ingested`. Prints 3 lines plus `next:` (4 max). `--json` data has counts, paths and warning strings only.
  On a `CvtError` it sets `status=failed`, appends `errors[]` and a history entry, saves, and re-raises. A re-run with identical
  texts on a run already past `ingested` is a no-op (stage kept, nothing marked stale).
- Real sample CV: 6 pages, 278 lines, email once, no U+200B/❖/➢, "Role: SRE" twice, "Altimetrik ... Feb 2024 - Present" on one line.
- Deterministic cleanup: the junior `.txt` fixture is line- and content-identical after NFKC (tested).

## Deviations
- Repeated-header matching is stricter than the brief's "digit-stripped" rule. Lines longer than `MAX_DIGIT_VARIANT_CHARS = 40`
  count as repeated only when identical after whitespace normalization (short lines such as "Page 2 of 6" still match when
  only digits differ). Bullet lines (leading decorative glyph) are never header candidates. Reason: a digit-only match
  deleted real bullets ("service number 4" vs "5") in my synthetic PDF, which breaks "without losing content".
- The kept header is hoisted to line 1 only when its first occurrence is a top line of a page after the first content page
  (the sample's email header first appears on page 2). The warning reads "moved N repeated header line(s) to the top of the CV".
- `◆` is a mid-line separator (` | `) as well as `♦`.
- `url` JD: the fetched text is saved to `inputs/jd.md` with a leading `<!-- jd-url: URL -->` line, and `state.inputs.jd.sha256`
  is updated. Only `http`/`https` are fetched (a `file://` URL gets exit 5, `E_JD_FETCH`). A re-run reuses the saved text.
- Added error ids: `E_CV_SCANNED`, `E_CV_DOCX`, `E_CV_UNREADABLE`, `E_CV_EMPTY`, `E_CV_FORMAT`, `E_JD_FETCH`, `E_JD_UNREADABLE`,
  `E_JD_EMPTY`, `E_MISSING_DEPENDENCY`.
- interfaces.md section 5 says `.docx` gives `CvtError(INPUT)` and the url error is `E_JD_FETCH`. I followed the brief
  (extras hook) and the section 5 id.

## ESCALATION
- File: `plan/contracts/state.schema.json`, `$defs`/`ingest.method` enum (`none|pdftotext|pypdf|text|markdown|docx`).
- Problem: the brief asks for method `ocr` when `extras.ocr_pdf` handles a scanned PDF, but the enum has no `ocr`.
  `Extraction.method` is `"ocr"` in memory. The command stores `"none"` (`OCR_STATE_METHOD`), and the warning
  "scanned PDF: text came from OCR..." and `scanned_suspect=true` are recorded.
- Proposed fix: add `"ocr"` to the enum (also in `assets/schemas/state.schema.json`), then set `OCR_STATE_METHOD = "ocr"`
  in `commands/ingest.py`. The OCR branch is covered at the `extract_cv` level only, so a test of the stored value waits on this.
