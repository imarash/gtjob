# WP-26 report: `gtjob` CLI end to end with a fake model, and cross-host resume

Status: DONE. Acceptance 1/1 pass (11 tests, no network, no API key). `tests/unit`: 1124 passed.

## Summary

- `tests/e2e/test_cli_offline.py` (7 tests) runs the real `gtjob` flow, stages, LLM cache, config and `cvtlib`. Only the
  client is a `FakeClient`, injected into the production `ApiRunner` (`runner._client = fake`). This is not the
  `GTJOB_FAKE_LLM` hook, so the tests can read `fake.calls` (models, prompts) and the real response cache stays under
  the temporary workspace.
- `tests/e2e/test_cross_host.py` (4 tests) runs the IDE side as real `cvt.py` subprocesses (`GTJOB_HOST=cursor`, once
  `claude_code`) and the CLI side as `gtjob`. Both handoff directions and the checkpoint 2 handoff are covered.
- `tests/e2e/fake_llm/`: `profile`, `jd`, `match`, `questions`, `answer_parse`, `change_request`, `tailor.2` (good plan)
  come from the junior goldens. `tailor.1` is the deliberately bad answer (a rewritten bullet adds "Kubernetes").
  `jd-bad.json` (wrong `jd_sha256`) and `tailor-auto.json` (the plan without the attested Helm bullet or skill) are used
  only when a test asks for them. `FakeClient.from_dir` ignores both, because their names are not `<stage>[.N].json`.

- **Fix loop:** the first tailor answer fails `check-tailored`. The retry is the `fix` packet on top of the original turn
  (`history` = user + assistant, one block starting `# Stage: fix`, naming Kubernetes and `exp-1.b2`, no JD text, no plan
  text). The final `tailor-plan.json` and `tailored.json` have no Kubernetes, and `check-tailored` passes.
- **Routing:** every call uses the model from section 14.6 (`jd`, `answer_parse`, `change_request` on Haiku; the others on
  Sonnet). A passing `jd-check` makes one `jd` call. A bad `jd` answer makes exactly `[haiku, sonnet]`, and the retry is a
  fix packet.
- **Usage:** the table is printed with header and total. `usage.jsonl` has `kind: api` rows for six stages with synthetic
  input and output tokens > 0, and tailor attempts `[1, 2]`.
- **`--auto`:** no `answer_parse` call, no attestation store content, `attestations_used == []`.
- **LLM cache:** run 2 (same inputs, new slug) makes no `profile` or `jd` call (stored profile, earlier `jd.json`). Run 3 is
  the same run again (`out/` removed, so the same slug and prompts) and makes 0 `FakeClient` calls and writes no `api` usage
  rows. With `--no-cache` it calls `jd, match, questions, tailor` again.
- **status / render / profile:** `gtjob status RUN`, `render RUN --template classic` (`build/render.json` theme is classic;
  the run stays `rendered` or `validated`), `profile list --person` (one active "Helm").
- **edit:** `gtjob edit RUN --text ...` makes one `change_request` call on Haiku, `tailored.json` version + 1, the dropped

  `answer_parse, tailor, tailor`. `kind: packet` counts for `profile, jd, match, questions` are unchanged. History hosts are

- **CLI -> IDE (checkpoint 1):** non-TTY `gtjob tailor` exits 6 with the questions printed. Then `cvt answers-apply --round

- **Checkpoint 2 handoff:** the CLI exits 6 at `awaiting_approval`. Then `cvt apply-edits` + `cvt approve --all`, then

## Deviations

- Commands ran as `uv run --no-sync pytest ...`. Plain `uv run` tries to reinstall the editable `gtjob` project and fails in
  the sandbox (`failed to remove .venv/bin/gtjob: Operation not permitted`). It is the same pytest from the same venv.
- The fake client is injected through `ApiRunner._client`, not through `GTJOB_FAKE_LLM` (reason in Summary). The hook is
  already covered by WP-I4's `test_wave4.py`. The autouse fixture removes it from the environment.
- `test_cross_host.py` imports helpers with `from .test_cli_offline import ...` because another worker's
  `tests/e2e/__init__.py` makes `e2e` a package. If that file is removed, the import becomes
  `from test_cli_offline import ...`.
- `cvt diff` exits 0 when it presents checkpoint 2 (the stage becomes `awaiting_approval`). The brief's "continue with raw cvt
  commands" is tested with that behavior.
- "Second identical run hits the LLM cache" is split in two. A new run gets a new slug, which is part of every packet, so
  only profile and JD reuse (0 calls) apply there. The literal LLM-cache hit needs the same slug, so `out/` is removed first.
