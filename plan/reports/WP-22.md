# WP-22 report: `gtjob` CLI commands and the terminal interaction model

Status: DONE. Acceptance 2/2 pass. `uv run pytest -q tests/unit`: 1107 passed, 1 skipped.

## Summary

- `flow.drive` is a state-driven stage loop. It runs deterministic steps through `cvtlib.cli.main` in-process and AI
  stages through an injected `Runner`. Because it only reads `state.json`, runs started in Cursor or Claude Code resume
  here and the reverse (tested: `questions` run under host `cursor`, finished under host `cli`).
- Checkpoint 1: `--answers` YAML, `continue --text` (routed to `answer_parse`), terminal prompts, `--auto`, and a non-TTY
  stop (prints the questions, exit 6). Free text goes `answer_parse` → dry-run plan shown → follow-up skeletons added with
  `questions --add` → confirm (terminal only) → commit. Choice ids go through `answers.select_round`, then
  `answers-apply --round ... --commit`.
- Checkpoint 2: compact diff, then `a`, `r N`, `e N <text>`, `d` (full diff), `q`, or free text → `change_request` →
  `apply-edits`. `r` and `e` build edits files deterministically (no AI). YAML `checkpoint2` is `approve_all` or a list of
  instructions followed by approve. `continue --text` / `edit` after approval re-enter checkpoint 2.
- `cli.py`: `tailor`, `continue`, `status`, `render`, `edit`, `profile`, `package-skill`, plus an optional `serve` through
  `gtjob.web.serve.register` when that module exists. `main()` sets `GTJOB_HOST=cli` first. `ApiRunner` wraps WP-21.
- A per-stage usage table (stage, model, input, cache read, output, total) prints at the end of a run or stop.

## Design notes and deviations

1. **Runner contract.** `flow.Runner.run_stage(stage, run_dir, *, extra=None, interactive=False) -> Path` is the only AI
   dependency. `interactive` is forwarded to the stage runner. `ApiRunner` turns it into `GtjobConfig.interactive`
   (1-hour cache TTL) with `dataclasses.replace`.
2. **Checked vs unchecked.** WP-21's `run_stage_checked` runs the check command and raises on any non-zero exit, so
   `ApiRunner` uses it for `profile`, `jd`, `match`, `answer_parse`, `tailor` and `critic`. It uses plain `run_stage` for:
   - `questions`, because its check exits 6 by design.
   - `change_request`, because `apply-edits` is not idempotent.

   The flow runs those two checks itself. For the others it runs the follow-up check (`profile-build`, `jd-check`,
   `match-check`, `assemble`) only if `state.stage` did not move, so nothing runs twice (tested with a "checked" fake).
   Trade-off: `questions` and `apply-edits` get no automatic fix loop. A violation prints with its hint and stops (exit
   1) or re-prompts (checkpoint 2).
3. **`default_rest` and follow-ups.** `default_rest` at checkpoint 1 defaults only the questions that were pending when
   the answer was given. Follow-ups created by that reply (for example the Helm scope question) stay pending and take
   `followups: default` or a prompt. Without it, a non-TTY run stops with exit 6 at the follow-up.
4. **`default_rest` mechanics.** It is implemented as `answers.select_round(..., default_rest=False)` plus
   `unmentioned_question_ids`, committed with `answers-apply --round`. Same selection code, but the command's own
   `--default-rest` is not used because it would also default new follow-ups.
5. **Extra `drive` kwargs.** `reply`, `critic` and `critic_visual` are optional and keyword-only. `critic` is not in the
   state schema, so it is passed in-process.
6. **`gtjob render`.** Without `--template` it runs `fit` then `validate`. With `--template` it runs `cvt render
   --template T` then `validate`, because `fit` takes its template from `tailored.json` and cannot override it.
7. **`profile`** also accepts `activate`. `revoke` shows the attestation first and asks for confirmation on a TTY. Off a
   TTY it needs `--yes` (exit 2 otherwise).
8. `ScriptedIO` accepts callables as inputs, so a test can compute an item number when it is asked.
